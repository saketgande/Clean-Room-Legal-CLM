How output becomes action. Background jobs: the model must answer through one forced tool shaped by a Pydantic form; code validates it, checks each quote against the stored text, then writes rows. Chat: the model calls a tool; anything that changes data waits for a card. Both designs are right. The weakness is inside the chat tools and in what the model knows when choosing one.

  • One model, claude-sonnet-4-6, for all 3,017 real calls. A per-feature model field exists and is never set.
  • Chat caching works for the fixed part: the system prompt and the tool list are cache-marked (integrations/claude.py:226-250); 62% of chat input tokens were cache reads. Messages are not marked, so tool results inside a turn are re-billed each round.
  • Jobs do not share the contract. The contract text sits in the user turn after the task text, so the four or five jobs on each upload each pay full price for it.
  • Contract input: whole text up to 400,000 characters, then cut with a flag while the job still succeeds.
  • Cut-offs: jobs reject a cut-off answer and fail with a plain reason (correct). All 19 metadata failures were cut-offs at 4,096. Chat does not check.
  • Budget: 5M tokens a day for the organisation; guardrail calls are outside it; no per-user budget.

Strategy. (1) Keep one main model; you chose it, and the routing test scored a small model 0.64 against 0.90. Add the ability to set a model per task and test only the tiny classifiers. (2) Put the contract text in its own cached block ahead of the task text. (3) Give chat a briefing and a clause reader so whole-contract reading is the exception. (4) Cap tool results, say when cut, and carry a compact copy forward. (5) Check the stop reason in chat and warn on the last round.

10. Background AI: what works

This side is in better shape than the chat, and the report should say so. Read in controller.py:1148-1785:

  • AI never overwrites a person. Metadata fills a blank or refreshes a value AI wrote earlier; never a person's or the form's (:1544-1555).
  • The model's own character offsets are never stored; the text it returned is located in the snapshot (:1609-1616). The comment records why: 57% of model offsets were wrong.
  • An empty extraction cannot wipe existing clauses (:1675-1681).
  • Unchanged text is not paid for twice: an identical earlier snapshot's result is reused if prompt, model and skill version match (:141-253).
  • A failed call is never replaced by a guess, and the failure reason is a plain sentence (:1348-1380).
  • Weak spot: when a quote check fails, the run is marked "needs review" but its rows are still written (:1286-1308).

Since 24 Oct, when test runs stopped writing to dev: metadata 33 ok, 3 cut off; clauses 36 ok; obligations 6 ok, 1 failed; renewals 4 ok; table cells 73 ok; table rows 0 of 3; template checks 38 ok, 4 failed. Engine totals on dev: 38 form requests, all 38 got a workflow and a contract, 25 reached signature, 10 are signed.

Data hygiene new. Dev still holds about 4,300 failed triage and screening job rows and 1,625 cancelled extraction rows from before 23 Oct, all from test runs ("UPDATE… expected to update 1 row; 0 were matched"). Any dashboard built on this table will show a false 80% failure rate until they are cleared.
